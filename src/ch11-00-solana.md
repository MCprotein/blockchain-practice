# 11. Solana의 계정과 프로그램 모델

Solana 스마트 컨트랙트도 Rust로 작성한다. Solana에서는 보통 스마트 컨트랙트 대신 프로그램(program)이라고 부른다. EVM 경험자가 가장 먼저 바꿔야 할 생각은 “프로그램 안에 상태가 있다”가 아니라 “프로그램 코드와 상태 계정이 분리된다”는 점이다.

## Ethereum과 비교

| Ethereum | Solana |
|---|---|
| 컨트랙트 주소에 코드와 storage가 연결됨 | 실행 프로그램과 데이터를 담은 계정이 분리됨 |
| 호출 중 storage 슬롯을 읽고 씀 | instruction이 사용할 계정 목록을 전달받음 |
| `msg.sender`로 현재 호출자를 확인 | `Signer` 여부와 전달된 계정 제약을 확인 |
| 다른 컨트랙트를 call | CPI(Cross Program Invocation)로 다른 프로그램 호출 |
| gas | compute unit과 트랜잭션 수수료 |

Solana 트랜잭션은 읽고 쓸 계정을 미리 명시한다. 런타임은 이 정보를 보고 서로 충돌하지 않는 트랜잭션을 병렬로 처리한다.

## 계정은 상태의 기본 단위다

Solana 계정에는 대략 다음 필드가 있다.

- `lamports`: 계정이 보유한 SOL의 최소 단위
- `data`: 프로그램이 정의한 바이트 데이터
- `owner`: 이 계정의 데이터를 수정할 권한이 있는 프로그램 ID
- `executable`: 프로그램 코드를 담은 실행 계정인지 여부
- `rent_epoch`: rent 처리와 관련된 런타임 필드

여기서 `owner`는 “이 자산을 가진 사용자”라는 뜻이 아니다. 계정의 `data`를 어떤 프로그램이 수정할 수 있는지를 나타낸다. 사용자 소유권은 데이터 안의 authority 필드나 토큰 계정 규칙으로 따로 표현한다.

## Instruction이 프로그램을 호출한다

Instruction은 세 덩어리로 볼 수 있다.

```text
program_id: 실행할 프로그램
accounts: 읽기/쓰기·서명 여부를 표시한 계정 목록
data: 실행할 명령과 인자
```

프로그램은 전달받은 계정을 무조건 믿으면 안 된다. 예상한 주소인지, 올바른 프로그램이 소유하는지, 쓰기 가능한지, 필요한 서명이 있는지, 데이터 타입이 맞는지 검증해야 한다. Anchor의 계정 제약은 이 반복 검사를 선언적으로 작성하도록 돕는다.

## PDA는 프로그램이 제어하는 주소다

PDA(Program Derived Address)는 프로그램 ID와 시드(seed)로 결정적으로 구한 주소다. 타원곡선 공개키 영역 밖의 주소(off-curve address)로 만들어져 대응하는 개인키가 없다.

```text
PDA = derive(program_id, seeds, bump)
```

예를 들어 사용자마다 하나의 Vault 상태를 만들 수 있다.

```text
seeds = ["vault", user_public_key]
```

같은 프로그램 ID와 시드를 쓰면 클라이언트와 프로그램이 같은 주소를 계산한다. `bump`는 유효한 곡선 밖 주소를 찾기 위해 함께 쓰는 작은 값이다.

PDA는 개인키로 서명하지 않는다. 프로그램이 CPI를 보낼 때 런타임에 동일한 시드와 bump를 제시하면 런타임이 그 PDA를 해당 프로그램의 서명자로 취급한다. “프로그램이 PDA의 개인키를 가진다”라고 설명하면 틀리다.

## CPI는 프로그램 간 호출이다

CPI(Cross Program Invocation)는 실행 중인 프로그램이 다른 프로그램의 instruction을 호출하는 방식이다. 토큰 전송을 위해 Token Program을 부르는 것이 대표적이다.

호출자는 자신이 받은 계정 권한보다 더 큰 권한을 아래 프로그램에 줄 수 없다. 원래 읽기 전용으로 전달된 계정을 CPI에서 쓰기 가능으로 바꾸거나 서명하지 않은 사용자를 서명자로 만들 수 없다. PDA 서명만 해당 프로그램의 시드 검증을 거쳐 런타임이 대신 부여한다.

```text
사용자 트랜잭션
  └─ Vault Program
       └─ CPI → Token Program
                    └─ 토큰 계정 잔액 변경
```

CPI 전후에도 회계 불변식을 생각해야 한다. 악성 프로그램 주소를 Token Program인 것처럼 넘기지 못하게 프로그램 ID를 타입이나 주소 제약으로 고정한다.

## 계정 검증에서 자주 나는 문제

- 서명자 확인 누락: authority 공개키만 같고 실제 서명이 없어도 통과함
- owner 확인 누락: 공격자가 같은 바이트 모양의 임의 계정을 전달함
- PDA seed 불일치: 다른 사용자의 상태 계정을 끼워 넣음
- 쓰기 권한 오표기: 바꿔야 할 계정이 read-only라 실행이 실패함
- 중복 가변 계정: 서로 달라야 할 두 역할에 같은 계정을 넣음
- 계정 종료 처리 실수: lamports와 데이터를 정리한 뒤 다시 쓰일 여지를 남김

EVM에서 `msg.sender`, allowance, reentrancy를 의심했다면 Solana에서는 “전달된 각 계정이 정말 그 역할인가”를 먼저 의심해야 한다.

핵심 확인 질문은 하나다. 프로그램이 받은 모든 계정에 대해 주소, 소유 프로그램, 서명, 쓰기 권한을 검증했는가?
