# 6. Ethereum 트랜잭션, EVM, 가스

Ethereum은 블록체인 위에서 범용 상태 전이를 실행한다. 사용자는 서명한 트랜잭션을 보내고 EVM(Ethereum Virtual Machine)은 트랜잭션에 담긴 호출을 실행해 세계 상태를 바꾼다.

## 계정과 상태

입문 단계에서는 계정을 두 종류로 나누면 충분하다.

- 외부 소유 계정(EOA): 키로 제어하며 트랜잭션을 시작한다.
- 컨트랙트 계정: 배포된 코드와 저장 상태를 가지며 호출에 따라 실행된다.

컨트랙트가 스스로 깨어나 예약 작업을 수행하지는 않는다. 어떤 트랜잭션이나 다른 컨트랙트 호출이 실행을 시작해야 한다. 크론 작업이 필요하면 오프체인 자동화 서비스가 조건을 감시하고 트랜잭션을 보낸다.

## 트랜잭션에 들어가는 값

일반적인 EIP-1559 형식의 트랜잭션에는 다음 값이 중요하다.

| 필드 | 의미 |
|---|---|
| `chainId` | 다른 체인에서 같은 서명이 재사용되는 것을 막는 체인 식별자 |
| `nonce` | 해당 발신자가 보낸 트랜잭션의 순번 |
| `to` | 수신 계정 또는 호출할 컨트랙트 |
| `value` | 함께 보낼 ETH 양 |
| `data` | ABI 규칙으로 인코딩한 함수 선택자와 인자, 또는 컨트랙트 생성 코드 |
| `gasLimit` | 이 트랜잭션이 소비할 수 있는 최대 가스 |
| `maxFeePerGas` | 가스 한 단위에 지불할 총가격 상한 |
| `maxPriorityFeePerGas` | 검증자에게 줄 우선 수수료 상한 |
| `signature` | 발신자의 승인 증명 |

EOA의 `nonce`는 0부터 순서대로 소비된다. 같은 nonce의 트랜잭션은 둘 다 확정될 수 없고 대기 중인 트랜잭션을 더 높은 수수료의 같은 nonce 트랜잭션으로 교체할 수 있다. `data`의 첫 4바이트 함수 선택자는 호출할 함수 시그니처를 가리키며 뒤에는 ABI로 인코딩한 인자가 붙는다.

트랜잭션 해시는 영수증 번호와 비슷한 식별자다. 서명이 아니며 성공을 보장하지도 않는다. 블록에 포함된 뒤 실행이 revert될 수 있고 이때 상태 변경은 되돌아가지만 이미 사용한 계산 자원에 대한 가스는 든다.

## 가스는 두 값을 곱한다

가스(gas)는 계산과 저장 작업량의 단위다. 실제 비용은 사용한 가스와 가스 가격을 곱한다.

```text
transaction fee = gas used × effective gas price
```

`gasLimit`은 지출 ETH 자체가 아니라 실행량 상한이다. 남은 가스는 모두 태워 버리는 것이 아니라 사용하지 않은 만큼 청구되지 않는다. 반대로 실행 중 가스가 모자라면 out-of-gas로 실패한다.

저장소에 새 값을 쓰는 작업은 단순 덧셈보다 비싸다. 노드들이 장기간 상태를 보관해야 하기 때문이다. 컨트랙트는 온체인에 꼭 필요한 상태만 두고 검색용 원본 데이터는 이벤트와 인덱서에 맡기는 경우가 많다.

## EIP와 EIP-1559

EIP(Ethereum Improvement Proposal)는 Ethereum의 프로토콜, 네트워크, 인터페이스, 애플리케이션 표준 등에 대한 제안 문서다. 번호는 순번에 가까운 식별자이지 버전 번호가 아니다. EIP-1559는 그중 1559번 제안이며 2021년 London 업그레이드에 포함됐다.

EIP-1559 이후 일반 트랜잭션 수수료는 크게 두 부분으로 나뉜다.

- 기본 수수료(base fee): 프로토콜이 이전 블록의 가스 사용량에 따라 조정한다.
- 우선 수수료(priority fee, tip): 블록 포함을 유도하기 위해 검증자에게 지급한다.

블록의 목표 가스 사용량은 최대 용량의 절반이다. 이전 블록이 목표보다 많이 사용되면 다음 `baseFee`가 오르고 적게 사용되면 내린다. 블록이 최대치까지 찬 경우 한 블록 사이의 상승 폭은 최대 12.5%다.

트랜잭션이 포함되려면 `maxFeePerGas`가 해당 블록의 `baseFee` 이상이어야 한다. 이 조건에서 실제 가스당 가격은 다음 상한 안에서 결정된다.

```text
effective gas price = baseFee + min(
  maxPriorityFeePerGas,
  maxFeePerGas - baseFee
)
```

`baseFee`는 소각(burn)된다. 소각은 해당 ETH를 다시 쓸 수 없는 상태로 만들어 유통 공급에서 제거한다는 뜻이다. 다만 “소각이 있으니 ETH 공급량은 언제나 감소한다”는 결론은 틀리다. 같은 기간의 신규 발행량과 소각량을 함께 비교해야 순공급 변화를 알 수 있다.

## EVM이 실행하는 순서

트랜잭션이 블록에 포함되면 노드는 대략 다음 순서로 처리한다.

```text
서명·nonce·잔액 확인
        ↓
호출 대상과 calldata 해석
        ↓
EVM 바이트코드 실행
        ↓
성공: 상태와 로그 반영
실패: 상태 변경 되돌림, 사용한 가스는 청구
        ↓
영수증(receipt) 생성
```

Solidity 코드는 EVM 바이트코드로 컴파일된다. 실행 중 데이터 위치를 구분해 두면 코드가 훨씬 잘 읽힌다.

| 위치 | 수명과 성격 |
|---|---|
| `storage` | 컨트랙트 상태로 블록 사이에도 남는다. 쓰기 비용이 크다 |
| `memory` | 한 외부 호출 동안 쓰는 임시 메모리다 |
| `calldata` | 외부 호출 입력이 놓이는 읽기 전용 영역이다 |
| stack | EVM 명령이 작은 값을 계산할 때 사용한다 |

## 온체인과 오프체인의 경계

컨트랙트에 모든 비즈니스 로직을 넣는 것이 탈중앙화는 아니다. 다음은 보통 온체인에 둘 후보가 된다.

- 자산 소유권과 잔액
- 누구나 같은 방식으로 검증해야 하는 권한 규칙
- 결제와 정산의 핵심 불변식
- 다른 컨트랙트가 조합해서 호출할 공개 인터페이스

대용량 검색, 개인정보, 이메일 발송, 복잡한 통계, 외부 API 호출은 오프체인 서비스가 맡는 편이 낫다. 온체인과 오프체인의 경계가 시스템 설계의 핵심이다.

## 트랜잭션을 읽을 때 묻는 질문

Explorer에서 트랜잭션 하나를 열고 다음을 확인해 보자.

1. 발신자와 수신자는 누구인가?
2. ETH가 함께 이동했는가?
3. 어떤 함수와 인자가 calldata에 들어갔는가?
4. `gas used`와 `effective gas price`는 얼마인가?
5. 상태는 성공인가, revert인가?
6. 어떤 이벤트 로그가 남았는가?

이 여섯 항목을 읽었다면 Solidity 코드와 실제 체인 실행을 연결할 준비가 됐다.
